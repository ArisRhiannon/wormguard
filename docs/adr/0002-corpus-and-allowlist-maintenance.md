# ADR-0002: IoC corpus and allowlist maintenance

**Status**: Accepted · **Decider**: Aris Rhiannon · **Supersedes**: none ·
**Related**: ADR-0001 (offline static detection)

## Context

wormguard's value decays without maintenance. Two bundled datasets drive
most of its signal, and both go stale:

- `data/iocs.json` — the malware indicator corpus, built from the GitHub
  Advisory Database (`type=malware&ecosystem=npm`). New malware is published
  continuously; a frozen corpus stops catching new campaigns within weeks.
- `data/script-allowlist.json` — sha256 fingerprints of legitimate
  lifecycle-script bodies. New versions of popular native packages ship new
  script bodies; a frozen allowlist starts producing false `WG-INSTALL-SCRIPT`
  noise and weakens fingerprint-drift detection.

Additionally, `data/top-names.json` (the typosquat/legitimacy reference set)
must stay large and current — the false-positive baseline
(`docs/false-positive-baseline.md`) showed that an undersized list was the
primary driver of CI-gating false positives.

The naive answer — a cron that refreshes everything and publishes a new
version automatically — is unacceptable for a *security* tool: an
unattended pipeline that auto-publishes from an upstream feed is itself a
supply-chain attack surface. A poisoned or spoofed feed would flow, signed
with our provenance, straight into users' CI.

## Decision

1. **Automate fetching; gate shipping behind a human + an explicit release.**
   - `scripts/refresh-corpus.ts`, `scripts/refresh-allowlist.ts`, and
     `scripts/refresh-top-names.ts` are the only network-touching code; the
     runtime audit pipeline never touches the network.
   - The `refresh-corpus` GitHub workflow runs weekly (and on demand),
     validates the refreshed corpus inline (typecheck + full test suite +
     corpus-integrity), and opens a **pull request**. It never commits to
     `main` and never publishes.
   - Publishing remains gated behind an explicit GitHub release
     (`publish.yml`, `on: release: published`). Merging a refresh PR does not
     ship anything by itself.

2. **All curated data carries a citation.** IoC seeds (domains, wallets,
   script hashes) added by hand in `scripts/refresh-corpus.ts` must link the
   advisory/report they came from. Allowlist additions must be regenerated by
   the populator script (never hand-edited) and justified with the package's
   popularity and the vouched-for script body. See `CONTRIBUTING.md`.

3. **Human curation from research sources is a first-class, non-automated
   process.** Campaign indicators appear in human-written research (Socket,
   Aikido, StepSecurity, GitHub Security Lab, vendor write-ups) before they
   reach structured feeds. We deliberately do **not** scrape these: a scraper
   would ingest unvetted, possibly attacker-planted text. A maintainer reviews
   these sources ~weekly, extracts durable indicators, encodes them as cited
   seeds, and a second reviewer verifies each against its source.

## Consequences

- **+** New malware reaches users within a week of hitting GHSA, with a human
  in the loop and zero new attack surface from automation.
- **+** Provenance integrity is preserved: nothing is published without a
  deliberate, human-cut release.
- **+** Datasets stay auditable — every indicator is traceable to a cited
  source; every allowlist hash is reproducible from the populator script.
- **−** There is unavoidable human latency (the curation step and the release
  step are manual by design). This is the cost of not auto-publishing a
  security tool.
- **−** A PR opened by the default `GITHUB_TOKEN` does not auto-trigger the
  required CI checks; a maintainer must trigger them before merging the
  refresh PR. Documented in the workflow and the PR body it emits.
